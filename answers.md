# Answers

## 1. Reference analysis

**How did you identify reusable components, variants and shared theme tokens? Explain one boundary you chose and how you verified the recreation against the reference.**

I captured the CRM first (`scripts/capture-crm.mjs`: 81 screenshots of default, menu, sheet, dialog, hover, focus, selected and mobile states) and read its real CSS variables and computed styles into `docs/reference/tokens.md` instead of guessing colours, which gave 43 UI patterns (`docs/reference/component-inventory.md`) grouped into 26 components. One boundary: the win-probability bar in the table and the Discovery/Evaluation/Procurement bars in the company sheet are one `SegmentedMeter` with `size`/`tone` props plus a thin `ProgressRow` wrapper (`packages/ui/src/components/crm/segmented-meter.tsx`), not two components. I verified by rendering every component in the real preview (`scripts/check-previews.mjs`) and comparing 12 key ones at the same height with the reference (`docs/comparison/side-by-side/`, differences in `docs/comparison.md`). That comparison caught one mistake: the Notifications demo rendered closed, so I added `defaultOpen`.

## 2. Architecture and clean code

**Why did you choose this stack and separation of responsibilities? Show one practical SOLID/DRY decision and one abstraction or feature you avoided under KISS/YAGNI.**

MERN + TypeScript + Tailwind was the team's stack, and one Express server serves the API, the catalogue (`/`) and the admin (`/admin`) so cookies stay same-origin; pure publishing and access rules live in `packages/core`, HTTP and storage in `apps/api`, the installer in `packages/cli`, and the feature radar is a plugin that receives the admin guard, limiter and queue from the host instead of importing them. DRY: one `buildRegistryItem()` (`packages/core/src/registry.ts`) feeds Copy code, the installer and the agent prompt, so when the agent test found a CSS ordering bug, one `CSS_SETUP` constant fixed Copy code, the prompt and the Get started page (the zero-dependency CLI prints the same three lines). Redis and BullMQ were added later, but they are optional (without `REDIS_URL` the same interfaces run in memory) and each has a concrete job: the queue runs slow AI draft builds and bundles over `QUEUE_THRESHOLD_BYTES`, the rate limits protect login, registry and search, and the cache holds published catalogue documents and is cleared on every admin write. What I avoided under KISS/YAGNI: a roles system (one env-configured admin), separate object storage (bundle source is capped at 500 KB plus a 300 KB thumbnail, well inside a MongoDB document), and npm publishing (the CLI is served as a tarball from `/cli/kitbase.tgz`). Turborepo runs on top of the npm workspaces for a cached task graph (a repeat `build`/`typecheck` takes milliseconds) and `--filter` builds per Render service; I kept it to `turbo.json` only and skipped remote caching and per-package release tooling, since nothing is published.

## 3. Publishing consistency

**How do preview, copied code, installation and agent instructions stay on the same published version? What happens when an update fails or a component is unpublished?**

Publish copies the validated draft into an immutable `published` snapshot, and preview, copy, registry (installer) and prompt all read only that snapshot through `makeCatalog()` (`apps/api/src/services/catalog.ts`); the snapshot is cached for 60 s, but every admin write calls `forgetPublished()`, so changes show on the next request. The `packages/cache` unit tests cover invalidation, and all four outputs are built by one `buildRegistryItem()` from the published snapshot; on the live site a manual redeploy kept all components and their versions. A bad update is rejected with 422 and a list of reasons on save (or marked failed by the background job for large bundles) and checked again on publish, so the live snapshot is never replaced by an invalid one, and AI-generated bundles only ever become drafts. Unpublish or delete removes it from the list and makes detail, preview, copy, prompt and registry return 404, but copies already installed stay in consumer projects.

## 4. Security

**What could go wrong when previewing uploaded code, calling admin APIs or installing files into another project? Which protections did you implement and test, and what limitations remain?**

Uploaded code could steal cookies or call our API, customers could call admin APIs or upgrade themselves, and an installer could write outside the project or overwrite files. Uploaded code runs only in a separate-origin `iframe sandbox="allow-scripts"` with code sent by postMessage, origin checks and CSP `connect-src 'none'` (a probe was blocked from cookies, storage, parent and network: `docs/reference/isolation-probe.png`). Admin APIs use a separate cookie and JWT audience, SameSite=strict plus an Origin check, zod on every input and a sliding-window login limit, and the installer uses an allow-list path regex plus a resolved-inside-`src` check, never overwrites without `--overwrite` and never runs commands; all of this is tested, including a tampered `../../evil.tsx` registry response. Remaining limits: previews need `unsafe-eval`, a hostile preview can still burn CPU or draw misleading UI in its own frame, preview assets need `Access-Control-Allow-Origin: *`, rate limits fail open if Redis is down (and are per instance without `REDIS_URL`), and CLI/agent tokens never expire, they can only be revoked (browser sessions use a 15-minute access JWT plus a rotating 10-day refresh token with reuse detection).

## 5. AI ownership

**Which AI suggestion or assumption did you challenge, and what evidence supported your conclusion? Show how you checked that copied code, the install command and the agent prompt actually worked in consumer projects — not just inside the catalogue.**

I rejected the AI's first plan to use the shadcn CLI as the installer and wrote our own zero-dependency CLI, because the brief requires rejecting unsafe paths, no silent overwrite and env-token auth, and the unit tests in `packages/cli/test/lib.test.ts` plus a live install/uninstall in a clean app prove each; I also rejected a generated dependency set where Vitest 2 hoisted Vite 5 and `tsc` failed with TS2769, fixed by moving to Vitest 3. Outside the catalogue, `examples/consumer-cli` was installed with the real `npx <origin>/cli/kitbase.tgz add ...` and passes `tsc && vite build` (`docs/reference/consumer-cli.png`), and `examples/consumer-copy` builds from the Copy code text alone. In `examples/consumer-agent` an AI agent followed the copied prompt and succeeded (`RESULT.md`): it found a real bug (the Geist `@import` was ignored after Tailwind's rules, fixed with one shared `CSS_SETUP` constant), while two of its "corrections" were my own test-setup mistake (a pre-filled `package.json`). I don't trust AI-generated components either: the feature-radar builder's output must pass the same `validateBundle()` rules and is saved only as a draft, and the validator now rejects code that uses `React.*` without importing React, because our preview puts React in scope and would otherwise hide a bundle that fails in a real project.

## 6. Production ownership

**What checks convinced you the deployed project was ready? If a newly published component breaks after release, what would you inspect first, how would you restore service without losing data, and what would you communicate to the team?**

The project is deployed on Render (free plan, manual deploys) with MongoDB Atlas and Render Key Value, and on 2026-09-27 I checked the live site: `/api/health`, the catalogue, the admin and `/cli/kitbase.tgz` return 200, the catalogue lists 28 published components (5 premium), the preview renders from its separate origin with `sandbox="allow-scripts"` and the expected headers, and signed-out requests get 200 for free `button` but 401 for premium `data-table` and for the admin API. The live installer worked in a clean Vite + React + TS + Tailwind v4 app (`tsc --noEmit` and `vite build` passed), refused premium without a token, refused to overwrite a changed file and refused `../evil`; the app log shows `redis connected`, and after a manual redeploy all 28 components and their premium flags were still there, so data survives a redeploy. Journeys A and B (admin publish, grant and revoke Premium) still need an owner sign-in on the live site and are reported as pending; they passed locally (flow B 15/15 against Atlas), as did the 32/32 unit tests; on the live site the admin, premium and free sign-in and Block / Unblock were also checked. If a published component breaks, I would first look at the admin detail (draft vs published version), the preview's error message and the JSON logs (`component published`, `registry download`), then unpublish it or re-publish the previous bundle, which takes effect on the next request without a redeploy; drafts and snapshots are separate and the data stays in Atlas, so nothing is lost. I would tell the team which component and version broke, what was affected, and that anyone who installed it should re-run the installer with `--overwrite`.

## 7. Premium access

**How did you model account access separately from component publication and admin permissions? Show how a free or revoked customer is blocked from premium code through previews, direct URLs, CLI and agent integration, and explain what revocation cannot undo.**

There are three separate checks: publication status (drafts and unpublished items are `not_found` for everyone), the customer's plan against the component's access level in one `decideAccess()` (`packages/core/src/access.ts`), and admin rights, which use a different cookie and JWT audience so premium never means admin. The plan and the `disabled` flag are loaded from MongoDB on every request (cookie or `Bearer` token), so signed-out requests get 401 and free ones 403 on preview, copy, prompt and registry, direct URLs included and all `no-store`; a revoke, a disabled account or the admin switching a live component to premium (which updates the draft and the published snapshot) applies on the very next request, as the live checks show (signed-out 401 on premium routes, and Block / Unblock verified by signing in). Protection was also proven with a premium component uploaded at runtime that is not in the repo (flow B, 15/15). Revocation only stops future retrieval: code a customer already copied or installed stays in their project.
